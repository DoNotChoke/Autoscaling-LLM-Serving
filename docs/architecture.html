GPU LLM Serving Platform

Giữ nguyên lõi của sách (DCGM → Prometheus → KEDA → HPA → Deployment, Grafana để quan sát), rồi thêm model server (KServe hoặc Ray Serve chạy vLLM), gateway, scale node GPU, logging bằng Loki và các thành phần vận hành.

Sơ đồ tổng thể

Nhánh A (KServe) và nhánh B (Ray Serve) là hai lựa chọn thay thế cho nhau; nét đứt là thành phần tùy chọn. Cuộn ngang trên màn hình nhỏ.

Bốn luồng chạy trong hệ thống

Request

  1. Client gọi API tương thích OpenAI tới Envoy AI Gateway.
  2. Gateway xác thực, giới hạn theo token, chọn backend theo model.
  3. Request tới Service của InferenceService (A) hoặc Ray Serve (B).
  4. vLLM gộp request bằng continuous batching và stream token về.

Metrics → quyết định scale

  1. vLLM và DCGM exporter mở endpoint /metrics.
  2. Prometheus scrape qua ServiceMonitor / PodMonitor.
  3. KEDA chạy PromQL theo pollingInterval, đưa kết quả vào external metrics API.
  4. HPA tính ceil[current × metric / target] và chỉnh số replica.

Scale node GPU

  1. Pod mới ở trạng thái Pending vì hết GPU trống.
  2. Karpenter hoặc Cluster Autoscaler gọi cloud API thêm GPU node.
  3. GPU Operator khởi tạo driver và device plugin trên node mới.
  4. Pod được schedule, tải weights, qua readiness rồi nhận traffic.

Logs và traces

  1. Alloy (DaemonSet) đọc log container trên mỗi node.
  2. Gắn label namespace, pod, model rồi đẩy sang Loki.
  3. Loki lưu chunk ở object storage.
  4. Grafana truy vấn LogQL cạnh PromQL, dùng chung label để đối chiếu.

Metric tên vllm:* có thể đổi theo phiên bản vLLM. Hãy kiểm tra /metrics của đúng bản bạn chạy trước khi viết query.

Cấu hình mẫu

Nhánh A · InferenceService dùng KEDA 
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: llama3-8b
  namespace: llm-serving
  annotations:
    # tên mode khác nhau giữa các bản KServe
    serving.kserve.io/deploymentMode: RawDeployment
    serving.kserve.io/autoscalerClass: keda
spec:
  predictor:
    minReplicas: 2
    maxReplicas: 8
    model:
      modelFormat: { name: huggingface }
      storageUri: s3://models/llama3-8b-instruct
      resources:
        limits: { nvidia.com/gpu: "1", cpu: "8", memory: 48Gi }
    autoScaling:
      metrics:
        - type: External
          external:
            metric:
              backend: prometheus
              serverAddress: http://prometheus-operated.monitoring:9090
              query: >-
                sum(vllm:num_requests_running{namespace="llm-serving"})
                + sum(vllm:num_requests_waiting{namespace="llm-serving"})
            target: { type: Value, value: "8" }
Nếu tự quản lý Deployment · ScaledObject với 5 tham số của sách 
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: vllm-llama3
  namespace: llm-serving
spec:
  scaleTargetRef: { name: vllm-llama3 }
  minReplicaCount: 2        # cao hơn tải nền một chút
  maxReplicaCount: 8        # vừa trên đỉnh tải, trong quota GPU
  pollingInterval: 15
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:
          stabilizationWindowSeconds: 0
          policies: [{ type: Pods, value: 2, periodSeconds: 60 }]
        scaleDown:
          # dài hơn thời gian khởi động một replica
          stabilizationWindowSeconds: 900
          policies: [{ type: Pods, value: 1, periodSeconds: 120 }]
  triggers:
    - type: prometheus
      metricType: AverageValue   # threshold tính trên mỗi replica
      metadata:
        serverAddress: http://prometheus-operated.monitoring:9090
        query: >-
          sum(vllm:num_requests_running{namespace="llm-serving"})
          + sum(vllm:num_requests_waiting{namespace="llm-serving"})
        threshold: "8"

Hai mẫu minh họa cấu trúc. Tên field của KServe thay đổi theo phiên bản, hãy đối chiếu với tài liệu của bản bạn cài. Khi dùng autoscalerClass: keda, KServe tự sinh ScaledObject nên không cần viết thêm khối bên phải cho cùng workload.

Những điểm dễ sai khi chạy thật

  • Cold start dàiPull image vài GB, tải weights hàng chục GB, khởi tạo CUDA. Giảm bằng pre-pull image, LocalModelCache trên NVMe, pod placeholder ưu tiên thấp để giữ chỗ GPU, và startupProbe đủ dài.
  • Scale down làm rớt requestĐặt terminationGracePeriodSeconds lớn hơn request dài nhất, thêm preStop để drain, và PodDisruptionBudget cho phép Karpenter dọn node an toàn.
  • FlappingDùng giá trị trung bình theo thời gian, stabilization window scale-down dài hơn thời gian khởi động, và policy xóa từng pod một.
  • CPU và RAM làm nghẽn trước GPULớp API, tokenizer và xử lý thread cần đủ CPU và RAM. Nếu thiếu, GPU không bao giờ đạt ngưỡng và hệ thống không scale.
  • Scale-to-zeroKEDA không scale từ 0 theo resource metric. Với LLM mất hàng phút để lên, production nên giữ minReplicas ≥ 1; scale về 0 hợp với môi trường dev hoặc job theo hàng đợi.
  • Quota và chi phíĐặt maxReplicas trong quota GPU của tài khoản cloud, và cảnh báo khi số replica chạm trần để phân biệt đỉnh tải thật với tấn công.
